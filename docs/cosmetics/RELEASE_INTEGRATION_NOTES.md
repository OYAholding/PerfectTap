## 2. QA-01: fixed on release/1.2.0

**QA-01 (High, pre-existing)** was: `private.purchase_economy_item` granted the item even
when `apply_economy_delta` reported a duplicate `event_key`, so replaying an old key with a
different `p_item_id` granted that item for free.

**Fixed on release/1.2.0 by `supabase/migrations/20261127110000_economy_hardening.sql`**
(finding C1 there). A replay of the same purchase returns `duplicate`. Reusing the key for
anything else fails `invalid_payload`, and nothing is charged or granted. The release session's
regression is `supabase/tests/database/economy_hardening.test.sql`. This branch does not
duplicate the server fix.
`docs/cosmetics/qa/sql/purchase_item_duplicate_event_key.test.sql` is now a regression
test that asserts the fixed behaviour: **10/10** on the release/1.2.0 migration set (results in
`supabase/proposals/README.md`).

## 3. Server catalog (proposal only)

`supabase/proposals/2026112800_cosmetic_studio_catalog.sql` (+ pgTAP test, README) has an
inactive config version with the cosmetic rows, `private.economy_bundles` and an atomic
`purchase_economy_bundle`. It was **rebased onto and tested against the full release/1.2.0
migration set**, including the hardening and support-operations migrations. It has never been deployed.
Review feedback from the economy session is resolved:

- **F1 (high):** the cosmetic ids are registered **disabled** under every config version.
  A trigger also registers them under configs created later. `server_owned_items()`
  ignores `enabled`, so while a config is active, or during a containment, a client profile
  save cannot add cosmetic ids to `owned_items`. A guard trigger keeps cosmetic rows disabled
  in non-cosmetic configs, so a blanket "enable the shop" cannot sell them. For ids added
  before the proposal is applied while an authoritative config was already active, there is
  `private.strip_unpaid_cosmetic_items(p_dry_run)` (service role, dry run by default, audited).
  It removes cosmetic ids that have no `shop_purchase` ledger entry.
- **F2 (medium):** `purchase_economy_bundle` locks `economy` before `profile_data`
  (rule L1), the same order as `purchase_economy_item`.
- **F3 (low):** the event-key replay check runs before `already_owned`. The same bundle returns
  `duplicate`, and any other reuse returns `invalid_payload`. Items are granted only when the delta is `applied`.
- The PK change (`economy_shop_items` → `(config_version, item_id)`) does not conflict
  with the hardening migration: every lookup there filters by `config_version`, and
  nothing in release/1.2.0 uses `ON CONFLICT` on this table. It still needs the
  economy session's approval.

Until a config with cosmetics is active, authoritative mode shows cosmetics as preview-only.

## 4. Follow-ups that need PR #14 to land first

- Cross-device loadout sync: proposed in `docs/cosmetics/LOADOUT_SYNC_CONTRACT.md`
  (`equipped_cosmetics` jsonb; server wins except unacknowledged local slots; server
  validation; privacy; migration order). The pure helpers
  (`Models/Cosmetics/CosmeticLoadoutSync.swift`) and their tests are in this branch, but nothing is
  wired. `PlayerProfile` / `BackendCodec` / sanitize are release-owned. Until then
  the loadout is stored per device, per account.
- Item ids are `<collection>.<slotRawValue>` (e.g. `quack_attack.tapButton`). They live in
  `ownedItems` forever — use exactly these strings in any server catalog.
